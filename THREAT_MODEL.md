# Threat model

## Assets

Organization source code, scoped secrets, provider credentials, Git credentials, task outputs, and the Docker host.

## Trust boundaries

Browser → API, API/worker → broker, broker → Docker daemon, and workload → external services. Workload code is adversarial, including code generated by an agent and repository hooks.

## Controls

The API enforces tenant-scoped database access and role checks. The worker submits a narrow, signed execution request. The broker validates a fixed schema, image allowlist, limits, network mode, and expiration before calling Docker. Workloads are non-root, capability-free, no-new-privileges, read-only root filesystem, bounded tmpfs/workspace, and receive no host mounts except a task workspace volume. Events are structured and redacted before persistence.

## Residual risks

Docker isolation is not equivalent to a VM boundary. A Docker daemon compromise or kernel exploit can compromise the host. Use dedicated, patched hosts and consider Kata/Firecracker for untrusted multi-tenant deployments. Network policy is defense in depth and must be supplemented with host firewall and DNS policy.
